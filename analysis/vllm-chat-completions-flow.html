      完整调用时序图：从 HTTP 入站到 SSE / JSON 返回

      一次成功请求的主调用顺序。每一行对应一个可定位函数、明确的内部阶段，或跨线程/进程/网络边界； 右侧标签说明它是异步、同步、线程池、IPC、GPU 还是 SSE。

      读法：顶部九个阶段是后续章节的压缩索引；下方时序按编号自上而下执行。 → 表示调用方向，返回 表示控制流或数据回到上一层。 n>1、beam search、流式与非流式在图中单独标出分支。

      STAGE 1HTTP 入站路由、认证、校验
      STAGE 2OpenAI 服务层模型、模板、工具策略
      STAGE 3Renderer消息、媒体、模板、token
      STAGE 4参数与生成器SamplingParams、request id
      STAGE 5EngineCore 提交InputProcessor、IPC
      STAGE 6调度与 KVprefix cache、slot、抢占
      STAGE 7Worker 前向batch、MM encoder、model
      STAGE 8采样与推进grammar、logits、stop
      STAGE 9输出与响应detokenize、SSE、JSON
      调用类型 HTTP 网络 ASYNC 协程 SYNC 同步 THREAD 线程池 IPC 跨进程 GPU 计算 SSE 流式

      HTTP 入站、中间件与 FastAPI 参数解析

      5. 05 FastAPI → Pydantic ChatCompletionRequest.model_validate(body) SYNC 构造 messages、tools、stream、采样与 vLLM 扩展字段。
      6. 06 Pydantic → validators _materialize_tool_calls / validate_* / check_* SYNC stream_options、logprobs、tool_choice、structured outputs、cache_salt 等校验。
      7. 07 Route → cancellation wrapper with_cancellation.wrapper(...) ASYNC 并发等待 handler 与 listen_for_disconnect；先完成者胜出。
      8. 08 Route → load wrapper load_aware_call.wrapper(...) ASYNC 按需增/减 server_load_metrics；响应结束通过 background task 减计数。
      9. 09 FastAPI → route handler create_chat_completion(request, raw_request) ASYNC 读取 metrics header，取得 chat handler。
      10. 10 Route → app state chat(raw_request) SYNC 返回 app.state.openai_serving_chat。
      11. 11 Route → OpenAIServingChat handler.create_chat_completion(request, raw_request) ASYNC 进入 OpenAI 兼容服务层。

      调度、prefix cache 命中、KV slot 分配与抢占

      v1/engine/core.py · v1/core/sched/scheduler.py · v1/core/kv_cache_manager.py · block_pool.py
      1. 81 EngineCore run loop → step step_fn() → EngineCore.step() SYNC EngineCore 进程内的同步迭代循环。
      2. 82 step → Scheduler scheduler.schedule() SYNC 先 running，再 waiting；构建本步 SchedulerOutput。
      3. 83 schedule → KVCacheManager kv_cache_manager.get_computed_blocks(request) SYNC 首次调度时查询本地 prefix cache。
      4. 84 get_computed_blocks → coordinator coordinator.find_longest_cache_hit(request.block_hashes, max_cache_hit_length) SYNC 最多缓存到 num_tokens - 1，要求 block 对齐。
      5. 85 coordinator → BlockPool block_pool.get_cached_block(block_hash, group_ids) SYNC 按 hash + kv group 查缓存 block。
      6. 86 schedule → KVConnector connector.get_num_new_matched_tokens(request, local_hits) SYNC 可选外部 KV 命中；可能返回 async load 标志。
      7. 87 schedule → KVCacheManager kv_cache_manager.allocate_slots(...) SYNC 按 comp/new_comp/ext_comp/new/lookahead 布局分配。
      8. 88 allocate_slots → coordinator get_num_blocks_to_allocate(...) / allocate_new_computed_blocks(...) / allocate_new_blocks(...) SYNC 计算需求、增加命中 block 引用、分配新 block。
      9. 89 coordinator → BlockPool block_pool.get_new_blocks(num_blocks) SYNC 从 free queue 取 block，递增 ref count，必要时 evict hash 映射。
      10. 90 allocate_slots → cache coordinator.cache_blocks(request, num_tokens_to_cache) SYNC 把可提交的完整 block 写入 prefix cache。
      11. 91 Scheduler → preemption _preempt_request / kv_cache_manager.free / encoder_cache_manager.free SYNC allocate_slots 返回 None 时抢占并回 waiting；非立即客户端错误。
      12. 92 scheduler.schedule → output builder NewRequestData.from_request / _make_cached_request_data / SchedulerOutput(...) SYNC 写出 block ids、scheduled tokens、encoder inputs、spec tokens。
      13. 93 scheduler.schedule → state advance _update_after_schedule(scheduler_output) SYNC 推进 num_computed_tokens，清 finished ids。
      14. 94 EngineCore.step → model executor model_executor.execute_model(scheduler_output, non_block=True) SYNC 返回 Future；真正 worker 调用经 executor。
      15. 95 EngineCore.step → structured output scheduler.get_grammar_bitmask(scheduler_output) SYNC 为本步生成 grammar token mask。
      16. 96 EngineCore.step → future future.result() SYNC 等待模型前向；若返回 None，再进入 sample_tokens。

      一条 chat completion 请求并不是“API handler 直接调用模型”。它跨过 HTTP 与 Pydantic、 OpenAI 协议层、chat template/多模态 renderer、tokenizer、EngineCore 进程边界、 调度器和 worker，再由输出处理器反向汇合成 OpenAI JSON 或 SSE。最关键的分叉点是 request.stream：它决定 SamplingParams.output_kind 和 HTTP 响应类型， 而模型、调度、KV cache 与采样主体相同。

      Scheduler、KV cache 与 prefix cache

      调度器不区分“prefill 阶段”和“decode 阶段”，而是让每个请求的已计算 token 数追上目标 token 数。

      V1 Scheduler 的核心不变量很简洁：每个请求维护 num_computed_tokens；每一步为请求分配若干新 token 的 KV slot， 让已计算 token 数向 len(prompt) + len(output) + len(speculative draft) 追赶。 因此 chunked prefill、普通 decode、prefix cache 命中、preemption 和 speculative decoding 都统一成“本步调度多少 token”的问题。
